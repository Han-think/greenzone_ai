## 4. 결과를 설명할 때

- **9 = 기존 1차 후보 6곳(G01·G03·G05·G06·G07·G10) + 새 대안 A4-1·A6-1·A7-1.** 예비 후보는 G02·G04·G08·G09·G11입니다.
- Louvain은 도로거리 150m 이내 필지를 연결하고 γ=1, 시드 20회 중 modularity 최대 결과를 선택했습니다. 생활권 1곳=거점 1곳은 팀 설계 원칙이며 유일한 최적 해라는 뜻은 아닙니다.
- 도로폭 7m·보호시설 200m 조건은 새 대안 도로 지점 탐색 기준입니다. 기존 후보 전체를 같은 조건으로 다시 심사한 결과는 아닙니다.
- G01은 등록 도로폭 8m, 실폭도로 도형의 수직 단면으로 구한 추정 폭 5.3m입니다. 1차 코드의 REGISTERED_OK=True는 등록폭이 7m 이상이면 이 추정 폭과 관계없이 합격시키는 설정입니다. 따라서 단순 표기 오류로 단정하지 않습니다. 현장 유효폭은 별도 확인이 필요합니다. A6-1은 보호시설 이격 약 200.4m로 설정 경계에 가깝습니다.
- 가장 가까운 거점을 쓰면 평균 172.6m·300m 안 95.3%, 자기 생활권 거점을 쓰면 평균 195.2m·300m 안 84.1%입니다. 현재 건물 안내는 **자기 생활권 담당 제안**을 연결합니다.
- 개별 필지↔거점 거리행렬이 최종 출력에 없어 특정 집의 보행거리는 표시하지 않습니다. 거점 상세의 평균은 해당 생활권 전체 평균입니다.
- 팀의 수거 순회 3.22km는 차고지·일방통행·회전·정차가 검증된 운행 노선이 아닙니다. 이번에 추가한 162구간 기반 경로안은 별도 계산이며 이 수치를 재현한 값이 아닙니다(11절).
- 원본 `실사필요=false`도 운영 승인으로 해석하지 않습니다. 모든 거점의 실제 정차·보행 연속성·부지 사용 동의는 확인이 필요합니다.

전체 재현에는 `pyojebu.xlsx`, `TL_SPRD_MANAGE`, `TL_SPBD_BULD`의 SHP·DBF·SHX·좌표계 자료가 필요합니다. 이 브랜치의 raw는 비어 있고 중간 거리행렬도 없습니다. 받은 코드를 실행하거나 원천 분석을 재현했다고 보고하지 않습니다.

### 9-3. 결과를 주소와 연결하는 과정

1. 팀 2차 주거 GeoJSON의 key를 읽습니다. 대지구분 한 자리만 전자지도 0/1 → PNU 일반/산 1/2로 변환합니다.
2. 기존 sinwol1_demand.json의 같은 PNU 필지를 찾습니다. 좌표가 가깝다는 이유로 다른 지번을 붙이지 않습니다.
3. 원본 해시가 일치하는 주소 보완본에서 건물명을 가져옵니다. 모든 필지에 건물명이 등록돼 있다는 뜻은 아닙니다.
4. 팀 결과의 생활권 번호로 거점안을 연결합니다. 도로명주소·지번·건물명·좌표·등록 주거단위·담당 거점을 검색 응답으로 만듭니다.
5. 선택 결과를 지도와 상세 영역에 표시합니다. 개별 필지의 보행거리 행렬은 없으므로 임의 거리를 추가하지 않습니다.

`.gitattributes`의 `data/** -text`는 Git이 데이터 줄바꿈을 자동 변환하지 않게 합니다. 받은 원본 SHA256과 기동 시 버전 확인을 Windows/Linux에서 유지하기 위한 설정이며, 데이터 내용을 변환하거나 전역 Git 설정을 바꾸지 않습니다.

서버 시작 때 주소 보완본의 기준 원본 해시와 거점/생활권 파일의 출처 해시를 확인합니다. 필지 수가 요약과 다르거나 지번 연결이 실패하면 원본을 임의 보정하지 않고 자료 버전을 맞춥니다.

## 지도 도구를 바꾸는 것과 데이터 재사용의 차이

현재 서비스 지도는 카카오이며, 팀의 최신 클릭 주소 확인 기능도 포함합니다. 받은 greenzone2nd_map.html은 Leaflet로 GeoJSON 결과를 보여주는 별도 HTML입니다. 이 HTML의 검색/마커/탭 상태가 현재 서비스에 자동 연결되는 것은 아닙니다.

데이터 재사용은 같은 필지 좌표·생활권 도형·거점 파일을 그대로 읽는다는 뜻입니다. Leaflet로 바꾸려면 static/map.js와 HTML의 지도 SDK 연결을 다시 작성해야 합니다. 이번 통합에서는 지도 제공자를 바꾸지 않습니다.

Folium은 Python에서 Leaflet 기반 HTML 지도를 만드는 도구입니다. 이번 로컬 작업에서는 별도 보고용 지도를 직접 생성하도록 folium 0.20.0을 추가했습니다. 받은 2차 HTML이 Leaflet을 사용한다는 사실만으로 원본도 Folium으로 생성됐다고 단정하지 않습니다.

지도 클릭 주소 확인 출처: [카카오 공식 좌표→주소 예제](https://apis.map.kakao.com/web/sample/coord2addr/). 주소 검색창과 지도 클릭 주소 확인은 별도 동작입니다. Folium 보고용 지도에는 카카오 키를 전달하지 않습니다.

## 11. 분석 필터와 수거 경로안

### 별도 Leaflet 분석 화면

첫 화면 헤더의 `Leaflet 보기 / Folium 보기`는 각각 새 탭을 엽니다. `/analysis`의 `main.py/analysis_view`는 `templates/analysis.html`을 전달하고, `static/analysis.js`가 기존 `/api/map-data`의 같은 결과를 읽습니다. `analysis.css`는 두 보고 화면에만 적용합니다. 기존 카카오 화면·검색 상태·경로 계산은 별도로 유지합니다.

`initializeReport → changeAnalysisPlan → drawAnalysis` 순서로 읽습니다. 체크 변경은 도형을 다시 그리며, 생활권 변경·전체 보기 버튼만 지도 범위를 맞춥니다. 6곳 비교는 새 대안 3곳과 기존 9생활권 색면을 숨기고, 비교 수치는 받은 엑셀의 최근접 거점 기준을 사용합니다. 도로폭은 도로선 표시 조건이며 거점을 자동 제외하거나 재선정하는 조건이 아닙니다. 마커·도로의 팝업은 `textContent`로 만들어 받은 이름을 HTML로 실행하지 않습니다.

표시 대상: 현재 거점안, 9생활권 색면, 주거 필지, 팀 도로선, 보호시설 반경 200m, 1차 후보 11곳, 대안 2·3순위. 도로·보호시설은 주변 맥락을 함께 표시합니다. 작은 화면에서는 필터를 접어 지도를 먼저 보여주며 필터 제목을 눌러 펼칩니다. 화면에 사용법·범례·출처·해석 범위를 함께 둡니다.

받은 팀 분석 HTML과 같은 Leaflet 1.9.4를 사용합니다. [공식 예제](https://leafletjs.com/examples/quick-start/)를 따라 CDN의 JS/CSS와 OpenStreetMap 배경을 연결하고 출처를 표시합니다. 배경 로딩이 실패해도 받은 도로·거점 도형은 유지합니다. 이 화면에서 `/api/route`·YOLO·LLM 호출은 하지 않습니다.

### 두 분석 지도의 공통 색·범례

`folium_report.py/ZONE_COLORS`의 1~9 순서 색을 `main.py`가 두 템플릿에 전달합니다. Leaflet은 HTML의 JSON 목록을 읽고 Folium은 같은 Python 목록을 씁니다. 필지도 소속 생활권 색을 따릅니다. `templates/analysis_legend.html`은 두 화면의 공통 번호 범례, `static/analysis_map.css`는 옅은 배경·번호 마커 스타일입니다. 기존 거점은 초록 원, 새 대안은 주황 사각형, 도로는 진한 파랑, 보호시설 반경은 빨간 점선입니다. 표시를 바꾸어도 팀 비교표·생활권·거점 위치는 그대로입니다.

### 별도 Folium 분석 화면

`main.py/folium_view → templates/analysis_folium.html → iframe의 /analysis/folium-map → folium_report.py/build_folium_report` 순서로 읽습니다. Folium은 이미 읽은 `map_data()` 자료로 실제 HTML 지도를 만듭니다. 파일 수집·분석 재실행·생활권 재배정은 하지 않습니다. 함수와 `@app.get` 옆에 역할을 주석으로 적었습니다.

왼쪽에서 6곳/9곳·등록폭 전체/7m 이상을 선택해 적용합니다. 지도 오른쪽 위의 `LayerControl` 체크로 거점·필지·도로·보호시설·1차 후보·대안을 켜고 끕니다. 6곳에서는 9생활권 색면을 숨기고 필지 팝업에 원래 배정임을 표시합니다. 조건 적용 시 체크·확대가 초기화되며, Leaflet 보기의 생활권별 선택 기능과는 차이가 있습니다.

수치는 같은 비교표의 최근접 거점 행(9곳 172.6m/95.3%, 6곳 226.1m/79.1%)입니다. 도로폭은 표시 조건이며 비교 수치나 거점 선정에 새로 반영하지 않습니다. G01의 등록폭 8m와 도형 단면 추정 5.3m도 두 화면에서 같은 설명을 씁니다. 이름·주소는 HTML 글자 처리 후 팝업에 넣습니다.

추가 설치는 `requirements.txt`의 `folium==0.20.0`이며 별도 API 키는 없습니다. Folium/Leaflet 도구와 OpenStreetMap 배경은 인터넷 연결이 필요합니다. [공식 LayerControl 예제](https://python-visualization.github.io/folium/latest/user_guide/ui_elements/layer_control.html), [설치 버전](https://pypi.org/project/folium/0.20.0/)을 참고했습니다.

### 카카오 화면의 수거 순회 경로안

**후보지 목록 → 6곳/9곳 비교 → 도로폭 선택 → 수거 순회 경로안 펼치기 → 거점 체크·출발·복귀 선택 → 경로안 계산** 순서입니다. 생활권 보기와 수거 거점 선택은 별개입니다. 표시 조건·출발·복귀·거점 체크를 바꾸면 이전 경로는 지워집니다. 주민이 건물을 검색해 선택하면 원래 9생활권 안내로 돌아갑니다.

| 파일·함수 | 입력 → 하는 일 → 결과 |
|---|---|
| scripts/prepare_route_graph.py | 받은 도로 162구간·거점 9곳 → 도형 교차점과 거점 투영점에서 도로를 끊음 → data/processed/route_graph.json |
| route_planner.py / shortest_paths | 점별 이웃 목록·출발점 → 누적거리가 짧은 점부터 확인(다익스트라) → 목적지별 거리·이전 점 |
| route_planner.py / plan_route | 거점 ID·출발·도로폭·복귀 → 가까운 미방문 거점을 차례로 선택 → 순서·구간 좌표·도로 거리 |
| main.py / collection_route | GET /api/route의 조건 → plan_route 호출 → JSON 응답. 잘못된 조건·연결 불가는 422와 사유 |
| static/route.js | 선택 조건 → fetch 요청 → 순서·구간 거리·도로 접속거리 표시 → 카카오 지도 선·번호 표시 |
| static/map.js / drawAnalysisLayers | 도로폭·표시 체크 → 받은 도로·보호시설 200m 반경을 그림. 법정 보호구역 확정 경계가 아님 |

`@app.get('/api/route')`는 **그 URL로 GET 요청이 오면 바로 아래 함수를 실행하도록 등록**하는 데코레이터입니다. `def`는 함수를 정의하고 `return`은 응답할 값을 돌려줍니다. `?ids=G06,G01&start=G06&min_width=7&closed=true`의 각 값이 함수 매개변수에 들어갑니다. Python 결과 딕셔너리는 FastAPI가 JSON으로 전달합니다.

### 계산·표시 기준

- 구간은 준비한 도로망의 최단거리, 방문 순서는 최근접 이웃법입니다. 전체 순회의 최적 해를 보장하지 않습니다. 도로폭 전체/7m 이상 두 조건을 제공합니다.
- 준비된 JSON은 두 입력의 SHA256을 기록합니다. 웹 시작 시 불일치하면 멈추고 같은 버전으로 다시 준비하도록 안내합니다. 재생성: `.venv\Scripts\python.exe scripts\prepare_route_graph.py`.
- 등록폭 7m는 분석용 가정입니다. 교차점은 도형 교차 기준, 모든 도로는 양방향 근사입니다. 일방통행·회전 제한·입체교차·정차·실제 유효폭·차고지를 검증하지 않았습니다.
- 거점은 선택한 도로의 가까운 점으로 투영합니다. 40m 초과이면 계산을 보류합니다. **주황 실선**은 도로 경로이고, **회색 점선**은 실제 진입로가 확인되지 않은 관계선입니다. 관계선 길이는 도로 순회 거리에서 제외하고 거점별로 별도 표시합니다.
- 거점이 도로망에서 끊어져 있으면 전체 경로 결과를 내지 않습니다. 직선·외부 API·다른 도로 자료로 대체하지 않습니다. 팀 2차의 전체 입력 도로망이 아니므로 원 보고서의 3.22km와 같은 계산으로 해석하지 않습니다.
- 필터 비교 수치는 받은 엑셀의 최근접 거점 6곳/9곳 결과입니다. 주민 검색의 자기 생활권 배정과 구분합니다. 배출량·인구·생활권은 이 기능으로 재계산하지 않습니다.

경로안 자체는 현재 카카오 지도에 새 키·패키지 없이 연결했습니다. Folium 보고 지도 패키지 추가와 구분합니다. `현재 분석 보기 인쇄`는 카카오 화면의 브라우저 인쇄/PDF 저장 창을 열며 파일을 자동 저장하지 않습니다. 수식이 있는 좌표·교차점 보조 함수와 `@app`, 각 화면 함수 옆에 읽는 순서 주석을 넣었습니다.

### 12-5. DB 연결 기준과 진행 순서

SQL 참고본의 `sources`, `waste_items`, `item_aliases`, `item_rules` 이름을 먼저 재사용합니다.
`sources`에는 확인일·시행일·원문 경로·해시 등 메타정보 보강이 필요합니다. 이 SQL만으로 전체 배출 안내/RAG DB가 완성되지는 않습니다.
후속으로 지역별 `disposal_rules`, 조문/문단별 `knowledge_documents`를 설계하고, 수정 이력과 임베딩 색인의 저장 방식은 팀 DB 구성에 맞춰 결정합니다.
초기 JSON은 출처를 보존하는 적재용 스냅샷입니다. 연결 후 서비스 조회/관리자 수정의 정본은 팀에서 합의한 DB 하나로 맞춥니다.

1. DATA-01/02/03 원문 대조·품목 매핑 → CODE-02 품목/규격 검색과 공식 수수료 조회
2. CODE-01은 팀 브랜치 통합 코드의 화면 확인, CODE-03은 업로드/수동 수정 화면을 독립적으로 진행
3. 수업 API의 이미지 입력 지원·주소·모델 ID 확인 → CODE-04 분류 연결
4. DATA-04/05 지역 안내·법령 확보 → CODE-05 RAG 연결
5. CODE-06 관리자 수정과 DB/색인 반영 연결 → 사용자 전체 흐름 확인

외부 API 키는 서버 `.env`에만 둡니다. API 제공처/모델 ID·임베딩 모델·팀 DB 종류는 아직 확정되지 않았습니다.
LLM·임베딩 API가 없을 때도 수동 품목 선택과 구조화 DB 조회를 먼저 구현할 수 있습니다.
남은 작업의 완료 여부는 실제 업로드·조회·수정 결과로 판단합니다. 이 문서와 자료 복사만으로 기능 완료로 표시하지 않습니다.

### 읽을 코드 순서

### DB와 관리자 범위

추가 DB는 Python 내장 SQLite를 사용합니다. 기존 지도 분석 자료와 분리된 **배출 안내용 DB 하나**입니다.
`records`에 품목 규칙/문서 JSON과 버전, `history`에 이전/새 값·사유·계정·UTC 시각, `seeds`에 최초 적재 여부를 저장합니다.
원본 파일이 바뀌었다고 이미 수정한 DB 값을 자동 덮어쓰지 않습니다. 추후 원문 갱신은 차이를 검토하고 관리자 수정 또는 별도 버전 적재를 해야 합니다.
기존 프리뷰의 SQL 4테이블은 참고본으로 남깁니다. 팀 DB가 따로 정해지면 이 조회 함수의 내부를 바꾸고 화면 입출력은 유지합니다.
관리자는 현재 **기존 품목/규격·문서를 수정/사용 중지**할 수 있습니다. 새 문서 등록, 후보 승인/위치 수정, 회원가입은 구현 범위에 넣지 않았습니다.

서버 `.env`의 관리자 계정으로 로그인합니다. 비밀번호 미설정/16자 미만이면 로그인 기능을 닫습니다.
세션은 임의 토큰+HttpOnly/SameSite 쿠키로 8시간 보관하며 서버 재시작 시 사라집니다. 모든 자료 API는 서버에서 인증합니다.
변경 API는 전용 헤더·Origin 확인, 로그인 실패 횟수 제한, 수정 사유/버전 확인을 적용합니다. 외부 공유는 HTTPS 주소를 사용합니다.
초기 화면이 비어 있어도 관리자 API가 공개되는 구조가 아닙니다. API 키·비밀번호는 HTML/JavaScript나 Git에 넣지 않습니다.

웹 안내의 확인일을 시행일로 바꾸지 않습니다. 법령은 해당 버전 발췌이며 전체 법령·관련 법규의 완전 수집을 뜻하지 않습니다.

### 사용자 화면에 반영하는 조건

- 배출 요약 초기 14건(양천구/전국)은 `review_needed`로 DB에 보존. 강서구 5건은 적재하지 않음.
- 새로 확보한 5건은 `verified_excerpt`로 표시. 사용 상태·시행기간을 확인해 화면에 노출.
- 관리자가 법령을 검토 완료로 바꿀 때 공식 URL·확인일·시행일 필수. 미검토 문서는 사용자에게 확정 안내로 노출하지 않음.
- 금액은 규격별 DB 행만 조회하고 스냅샷 여부를 표시. 큰 물건의 실제 치수·개수는 사용자가 확인.
- 수정 후 다음 DB 조회에 바로 반영. 임베딩 색인이 아직 없어 색인 동기화 기능은 없음.

### 실제 확인 순서

1. 현재 D 가상환경에 Pillow 13.0.0 설치 완료. 서버 재시작 → 수거 경로안 전용 버튼/기존 지도 확인.
2. 사진 한 장 업로드·지우기 → 품목/규격/수량 변경 → 참고 금액/출처 확인.
3. 관리자 로그인 → 한 규칙의 사유 있는 수정 → 이력 이전/새 값 → 사용자 재조회로 반영 확인.
4. 미로그인 관리자 요청·미지원/과대 사진·잘못된 수량 처리 확인.

Grounding DINO와 Gemini는 사진 업로드 시 호출됩니다. 입력 사진은 서버 파일로 저장하지 않습니다. 모델 가중치는 첫 DINO 실행 때 Hugging Face에서 다운로드되므로 인터넷과 충분한 메모리가 필요합니다. 실제 사진별 정확도·지연은 별도 검증이 필요합니다.


### 수거 경로의 직접 방문 순서

`static/route.js`의 `manualRouteOrder`가 현재 체크한 거점의 직접 순서를 보관합니다.
번호 선택 시 `moveRouteStop`으로 배열 항목 하나를 옮기고 1번을 출발 거점으로 맞춥니다.
체크 해제한 거점은 제외, 새 체크는 마지막 추가, 조건 변경은 이전 지도 경로와 대기 요청을 무효화합니다.
`/api/route?order_mode=manual`은 전달한 ID 순서 그대로 방문합니다. 각 구간은 기존 다익스트라 경로를 사용합니다.
`order_mode=auto`는 기존 최근접 이웃법입니다. 직접 지정에서도 중복 ID·2~9개·출발 ID·도로 연결 여부를 서버에서 검증합니다.
복귀 체크 시 마지막에 1번을 한 번 추가합니다. 지도 번호·구간 목록은 계산 응답 순서로 표시합니다.
단순 최단 구간이 다음 방문 예정 거점 부근을 미리 통과할 수 있습니다. 통과와 작업 정차를 구분하며 우회 강제 기능은 없습니다.
입력 도로/수요/생활권 분석 원본은 변경하지 않았고 별도 도로 API는 추가하지 않았습니다.

Git 공유 범위는 팀 내비게이션/지도 거리 코드, 경로 직접 순서, 사진 업로드·수동 품목 안내, 관리자, 법령 근거와 문서입니다.
실제 .env·로컬 DB·가상환경·사진은 Git에 포함하지 않습니다. 실행 확인 전 항목은 위 표와 README를 따릅니다.
