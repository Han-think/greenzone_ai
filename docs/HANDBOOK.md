## 4. 결과를 설명할 때

- **9 = 기존 1차 후보 6곳(G01·G03·G05·G06·G07·G10) + 새 대안 A4-1·A6-1·A7-1.** 예비 후보는 G02·G04·G08·G09·G11입니다.
- Louvain은 도로거리 150m 이내 필지를 연결하고 γ=1, 시드 20회 중 modularity 최대 결과를 선택했습니다. 생활권 1곳=거점 1곳은 팀 설계 원칙이며 유일한 최적 해라는 뜻은 아닙니다.
- 도로폭 7m·보호시설 200m 조건은 새 대안 도로 지점 탐색 기준입니다. 기존 후보 전체를 같은 조건으로 다시 심사한 결과는 아닙니다.
- G01은 등록 도로폭 8m, 실폭도로 도형의 수직 단면으로 구한 추정 폭 5.3m입니다. 1차 코드의 REGISTERED_OK=True는 등록폭이 7m 이상이면 이 추정 폭과 관계없이 합격시키는 설정입니다. 따라서 단순 표기 오류로 단정하지 않습니다. 현장 유효폭은 별도 확인이 필요합니다. A6-1은 보호시설 이격 약 200.4m로 설정 경계에 가깝습니다.
- 가장 가까운 거점을 쓰면 평균 172.6m·300m 안 95.3%, 자기 생활권 거점을 쓰면 평균 195.2m·300m 안 84.1%입니다. 현재 건물 안내는 **자기 생활권 담당 제안**을 연결합니다.
- 개별 필지↔거점 거리행렬이 최종 출력에 없어 특정 집의 보행거리는 표시하지 않습니다. 거점 상세의 평균은 해당 생활권 전체 평균입니다.
- 수거 순회 3.22km는 차고지·일방통행·회전·정차가 검증된 운행 노선이 아닙니다. 이번 웹에는 노선이나 운행 순서를 만들어 넣지 않았습니다.
- 원본 `실사필요=false`도 운영 승인으로 해석하지 않습니다. 모든 거점의 실제 정차·보행 연속성·부지 사용 동의는 확인이 필요합니다.

지금 통합한 것은 탭·더보기·보유 데이터·지도 연결입니다. 외부 전체 주소검색·유사어 자동완성·위성보기·수거차 방문 순서·LLM/RAG를 완료한 것으로 표현하지 않습니다. 분석 전체 재현·현장 안전·운영 승인도 별도입니다.

## 도로 자료 확인 보충

1차 ZIP에는 `greenzone1st_layer_roads.geojson` 162구간이 있습니다. 도로명·등록 도로폭·도로위계·7m 이상/미만 등급이 있으며 D의 `data/received/team_results/roads.geojson`과 같은 파일입니다. 도로폭 판정 코드도 포함되어 있습니다. 단, raw는 .gitkeep만 있어 원본 TL_SPRD_MANAGE·TL_SPRD_RW 등 SHP 묶음은 없습니다.

2차 코드도 도로 중심선 그래프·다익스트라 거리·대안 지점 등록폭 7m 필터·거점 순회거리 계산을 포함합니다. 도로가 반영되지 않았다는 뜻이 아닙니다. 1차 내보낸 도로는 동 경계 150m 안과 교차하는 도로이고, 2차 거리 계산의 입력 범위는 경계 +500m이므로 이 레이어만으로 같은 계산을 재현했다고 할 수 없습니다.

현재 가벼운 웹은 도로선을 별도 레이어로 그리지 않고, 받은 후보별 폭·거리 결과를 표시합니다. 원본 SHP·개별 거리행렬 미수신은 재계산의 한계이며, 받은 결과를 지도·목록으로 안내하는 데 도로 분석이 전혀 없는 상태는 아닙니다.

`data/received/archive/tradeoff_6853.png`는 6,853 주거단위 기반의 이전 후보 조합 비교 그림입니다. 현재 7,193 주거단위·9생활권 Louvain 안과 다른 버전이므로 수치를 섞지 않습니다.

1차 결과 엑셀·그림·HTML은 `data/received/team_results/first_stage*`, 설명서는 `analysis_report.md`에 보존합니다. 원본 코드 ZIP은 `data/received/archive/first_stage_source.zip`입니다. 임시 폴더의 5개 파일과 보존 경로·SHA256 대응은 같은 archive 폴더의 `source_delivery_manifest.json`에 기록했습니다. 임시 폴더를 웹 입력으로 읽지 않습니다.

### 9-3. 결과를 주소와 연결하는 과정

1. 팀 2차 주거 GeoJSON의 key를 읽습니다. 대지구분 한 자리만 전자지도 0/1 → PNU 일반/산 1/2로 변환합니다.
2. 기존 sinwol1_demand.json의 같은 PNU 필지를 찾습니다. 좌표가 가깝다는 이유로 다른 지번을 붙이지 않습니다.
3. 원본 해시가 일치하는 주소 보완본에서 건물명을 가져옵니다. 모든 필지에 건물명이 등록돼 있다는 뜻은 아닙니다.
4. 팀 결과의 생활권 번호로 거점안을 연결합니다. 도로명주소·지번·건물명·좌표·등록 주거단위·담당 거점을 검색 응답으로 만듭니다.
5. 선택 결과를 지도와 상세 영역에 표시합니다. 개별 필지의 보행거리 행렬은 없으므로 임의 거리를 추가하지 않습니다.

`.gitattributes`의 `data/** -text`는 Git이 데이터 줄바꿈을 자동 변환하지 않게 합니다. 받은 원본 SHA256과 기동 시 버전 확인을 Windows/Linux에서 유지하기 위한 설정이며, 데이터 내용을 변환하거나 전역 Git 설정을 바꾸지 않습니다.

서버 시작 때 주소 보완본의 기준 원본 해시와 거점/생활권 파일의 출처 해시를 확인합니다. 필지 수가 요약과 다르거나 지번 연결이 실패하면 원본을 임의 보정하지 않고 자료 버전을 맞춥니다.

### 9-4. 자료를 갱신할 때

현재 data에는 107개 파일, 목록에는 목록 자체를 제외한 106개 행이 있습니다. 이 개수는 정리 시점의 확인값입니다.

## 지도 도구를 바꾸는 것과 데이터 재사용의 차이

현재 서비스 지도는 카카오입니다. 받은 greenzone2nd_map.html은 Leaflet로 GeoJSON 결과를 보여주는 별도 HTML입니다. 이 HTML의 검색/마커/탭 상태가 현재 서비스에 자동 연결되는 것은 아닙니다.

데이터 재사용은 같은 필지 좌표·생활권 도형·거점 파일을 그대로 읽는다는 뜻입니다. Leaflet로 바꾸려면 static/map.js와 HTML의 지도 SDK 연결을 다시 작성해야 합니다. 이번 통합에서는 지도 제공자를 바꾸지 않습니다.

Folium은 Python에서 Leaflet 기반 HTML 지도를 만드는 도구입니다. 분석 보고용 지도 제작에 사용할 수 있지만, 현재 검색·탭·더보기를 붙이기 위해 설치할 필요는 없습니다. 받은 2차 HTML이 Leaflet을 사용한다는 사실만으로 Folium으로 생성됐다고 단정하지 않습니다.
