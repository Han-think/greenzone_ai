## 1. 이번 프로젝트의 마지막 완료선

**건물 검색으로 담당 제안 거점을 확인하고, 사진 또는 품목 검색에서 사용자가 품목·규격을 확정하면 공식 DB 안내를 받는다. 같은 배출 화면에서 추가 질문을 하면 검수 문서에 근거한 답변과 출처·날짜를 본다. 담당자는 안내를 수정할 수 있다. 이 과정을 다른 팀원 PC에서 재현하고 최종 발표 PDF로 설명한다.**

현재 사용자·관리자 기능과 사진 후보 확인은 로컬 시연 기록이 있다. RAG 질문 답변과 기존 화면 연결도 로컬에서 구현·확인했다. 현재 마무리의 중심은 독립 평가·팀 확인·발표 자료다. 현장 안전·부지 승인·실제 수거 효과는 미확인 목록으로 제출한다. 이것들을 이번 소프트웨어 완료의 선행조건으로 두면 일정이 끝나지 않으므로, **미확인 상태를 정확히 표시했는지**를 이번 제출 기준으로 삼는다.

## 분석·분산 배정의 마감 상태

팀 2차 분석은 필지 정제·주거단위 집계·도로거리·생활권·후보 연결·6/9/11곳 비교까지 결과가 있다. **새 분산배정 알고리즘이나 새 후보 발굴을 남은 필수 작업으로 배당하지 않는다.** 기존 결과를 현재 분석 산출물로 사용한다.

6곳안은 1차 후보에서 선택한 기존6곳, 9곳안은 그6곳에 후보가 없던 생활권의 대안3곳을 더한 비교안이다. 받은 표에서는 6곳 평균226.1m·300m이내79.1%, 9곳 자기생활권 담당점 평균195.2m·84.1%다. 이 비교만으로 비용·운영까지 포함한 절대 최적안은 정하지 않는다. 최종 발표에서 어느 안을 대표로 쓸지는 기존 비교표로 설명할 수 있다.

## 4. 코드 연결 약속 — 구현 전에 한 번 맞출 부분

아래 구성은 로컬에 구현됐다. 최초 계획의 세부 조건 중 독립 평가·다른 PC 재현은 계속 남는다.

| 파일 | 담당 | 변경 범위 |
|---|---|---|
| `guide_service.py` | 개발 B | `public_documents()`와 `make_guide()` 재사용. 현재 DB·이력 구조 활용 |
| `server/rag_service.py` 로컬 구현 | 개발 B | `build_index`, `search_documents`, `generate_answer`, `answer_question` 정도의 함수로 구성. 한국어 역할 주석 |
| `service_routes.py` | 개발 B | 기존 APIRouter에 질문 URL 하나 추가. 긴 요청은 기존처럼 `asyncio.to_thread` 사용 |
| `templates/disposal.html`, `static/disposal.js` | 개발 A | 기존 품목·규격 선택 아래에 추가 질문·근거 표시. 새 페이지 생성 없이 연결 |
| `requirements.txt`, `.env.example` | 개발 B | 실제 사용한 임베딩·LangChain 의존성과 설정만 기록. 키 값은 `.env` |
| `data/knowledge/` | 분석 A, 개발 B 반영 | 검수한 문서·평가 질문, 기존 원문과 출처 보존 |
| `README.md` | 분석 B/PM 취합 | 실행법·현재 상태·최종 화면·남은 한계 갱신 |

**색인 처리:** 매 질문마다 문서를 나누고 임베딩하지 않는다. 검수 문서로 한 번 색인을 만들고 질문 때 검색한다. 관리자 변경·시행일·검토 상태 등 입력 지문을 확인해 **다음 질문에서 자동 색인 갱신**한다. 문서 내용·수정 버전이 바뀌면 이전 색인을 재사용하지 않아야 한다. 새 관리자 색인 대시보드는 만들지 않는다.

**문서 필터:** 기존 `public_documents()`는 검토 상태와 시행일을 확인하지만, 시행일이 비어 있어도 통과할 수 있다. 비어 있다는 이유만으로 최신 법령이라고 간주하지 않는다. R1이 용도별 사용 가능 여부와 확인일을 검수하고, 조건·지역이 안 맞거나 효력이 불명확한 근거는 확정 답변에서 제외한다.

**추가 검색 범위:** 처음에는 검수한 보유 자료만 사용한다. 실시간 웹검색은 이번 필수 구현에서 제외한다. 자료 밖 질문은 공식 문의·직접 확인을 안내한다.

### 질문 API 입출력 제안

구현 URL: `POST /api/disposal/question`. 요청과 응답은 아래 형식을 사용한다.

```json
{
  "question": "이 소파는 어디서 신청하나요?",
  "item_id": "사용자가_선택한_공식품목ID_또는_null",
  "rule_id": "사용자가_선택한_규격ID_또는_null",
  "quantity": 1,
  "district": "신월1동"
}
```

```json
{
  "status": "answered",
  "answer": "검수한 근거에 따른 한국어 안내",
  "sources": [
    {
      "document_id": "실제_검색된_ID",
      "title": "공식 문서 제목",
      "url": "공식 원문 URL",
      "checked_at": "원문 확인일",
      "effective_from": null
    }
  ],
  "needed_fields": [],
  "notice": "그린존 제안 거점은 대형폐기물 공식 배출장소로 지정된 곳이 아닙니다."
}
```

- `answered`: 해당 조건을 뒷받침하는 근거가 있고 답변 가능.
- `needs_confirmation`: 규격·예약 정보·근거가 부족. 필요한 조건을 묻고 단정하지 않음. 확인에 도움이 되는 실제 검색 문서는 표시할 수 있으나 최종 결론의 근거처럼 쓰지 않음.
- `error`: 호출 실패·설정 오류. 사용자에게 다시 시도/수동 조회를 안내. 이를 “근거 없음”으로 기록하지 않음.

서버는 품목·규격 ID의 존재를 검증한다. 답변에 붙이는 출처는 **실제 검색 결과의 문서 ID에서 서버가 구성**한다. 모델이 만든 임의 URL은 쓰지 않는다. 규격이 없으면 금액 계산부터 하지 않고 규격을 묻는다. 선택된 규격은 `guide.make_guide()`의 DB 금액을 사용한다.

## 5. 시연 품목과 평가 질문 — 추가 선정 회의 없이 시작

시연 품목은 **소파·침대·장롱·밥상·서랍장**. 현재 공식 DB의 품목·규격 존재와 금액은 R1에서 다시 확인한다.

평가표 필수 열: `case_id, question, item_id, rule_id, expected_action, expected_answer, document_ids, source_urls, checked_at, effective_from, actual_answer, value_result, source_result, abstention_result, note`.
날짜가 원문에 없으면 `미명시`로 적는다. `value_result` 등은 통과/실패/해당없음으로 기록하고 분모를 함께 공개한다. 원본 질문10건·결과표는 `data/knowledge/` 아래 영어 이름의 파일로 저장하는 방향으로 준비한다. 아직 정답을 검수하지 않았으므로 계획만으로 파일을 “정답 확정” 처리하지 않는다.

## 7. 주말 코드 리뷰 순서

1. `main.py`: 어떤 URL을 연결하는지 본다.
2. 사용자 HTML/JS: 검색·사진·규격·질문이 어떤 요청을 보내는지 본다.
3. `service_routes.py`: 입력 검사와 함수 호출, 오류 응답을 따라간다.
4. `guide_service.py`: 원본 JSON→SQLite→수정 이력→사용자 재조회 흐름을 본다.
5. `vision_service.py`: 후보가 확정 품목이 되는 시점을 사람이 결정하는지 본다.
6. 추가된 RAG 파일: 근거 문서 선택·검색·출처 생성·보류 조건을 읽는다.
7. 지도·경로: 팀 분석값과 웹의 직선/도로 거리, 자동/직접 순서가 구분되는지 본다.
8. README와 PDF: 각 주장에 대응하는 화면·원본·실험 기록이 있는지 확인한다.

리뷰 결과는 `위치 / 이해한 역할 / 문제 또는 질문 / 담당 / 처리 상태` 다섯 칸으로 남긴다. 전체 구조 재설계는 하지 않고 시연을 막는 오류·근거 오안내·읽기 어려운 핵심 흐름을 우선 정리한다.

## 8. 중단 조건과 제출 판단

- RAG가 늦으면 임의 답변을 연결하지 않는다. 공식 DB 조회는 유지하고 RAG를 미완료로 표시해 강사와 제출 범위를 협의한다. 확정 요구사항이므로 조용히 완료 처리하지 않는다.
- 키/모델 제한은 오류로 표시하고 수동 조회가 이어지는지 확인한다. 외부 API가 되는 것처럼 캡처를 만들지 않는다.
- 실사·부지 동의를 못 받으면 미확인 표를 제출한다. 소프트웨어에서 거점을 승인 상태로 바꾸지 않는다.
- 추가 YOLO 학습·DINO·영상 관제·전국 확장·예약결제·새 지도·Docker/AWS 배포는 이번 필수 목록에 넣지 않는다.
- 제출은 **현재 코드 실행, RAG 평가, 자료·날짜 대조, PDF와 화면 일치** 네 조건으로 판단한다. 임의 전체 완료율은 쓰지 않는다.

팀에 지금 필요한 결정은 **역할별 실제 담당자, 발표 시간·제출 형식** 세 가지다. 나머지는 위의 입력·출력·완료 조건에 따라 진행할 수 있다.


## 9. 서버 폴더 이후의 실제 진행 위치 (2026-10-22)

서버 실행 폴더는 준비됐지만 R6 전체가 끝난 것은 아니다. 실행 진입 코드·설명은 완료했고 다른 팀 PC 재현과 최종 PDF는 남아 있다. RAG 모듈·질문 API·질문 화면도 현재 로컬 코드에 연결되어 있다.

```text
server/
  run.py                 # 현재 있음: 기존 main:app 실행
  rag_service.py         # 구현: 문서 색인·검색·Gemini 근거 답변
service_routes.py        # 기존 파일에 질문 API 연결 완료
static/disposal.js       # 질문 요청·답변 표시 연결 완료
templates/disposal.html  # 기존 화면에 질문칸 연결 완료
data/knowledge/          # 현재 있음: 공식 원문·발췌·품목·출처
data/local/rag_index/    # 첫 검색 때 생성: 검색 색인, Git 제외
```

문서 입력은 단순 JSON 직독보다 기존 `guide_service.public_documents()`를 사용해 관리자 수정·활성 상태를 반영한다. 색인은 첫 검색 때 만들고 내용/버전 변경 때 재구축하며 질문마다 재생성하지 않는다. API는 기존 서버 파일에 붙이므로 별도 RAG 서버나 포트를 만들지 않는다.

**팀 결정 없이 준비할 수 있는 순서**

1. 기본 평가9건과 별도 충돌 진단을 구분하고, 사진 원본의 외부 전송 없이 정답·규격·출처를 대조한다.
2. 기존 공식 문서의 지역·검토 상태·출처·확인일·시행일을 정리한다. 개인정보 평가 원본은 색인에 넣지 않는다.
3. 실제 계정에서 임베딩 모델 사용 가능 여부를 확인하고, 한 모델로 작은 문서 검색을 구현한다. 사용 가능 여부 확인 전 호출 성공으로 보고하지 않는다.
4. `server/rag_service.py`에서 검색→구조화된 Gemini 응답→서버 출처 검증을 연결한다. 금액은 기존 DB 조회.
5. 기존 배출 화면에 품목/규격 맥락과 질문을 전달하고 답변·출처·확인 요청을 표시한다.
6. 기본 평가·절차 질문을 실제 실행하고 Opik에는 비식별 결과만 기록한다. 독립 충돌 진단은 기본 성능과 따로 본다.
7. 기존 기능 확인·다른 PC 재현·발표 PDF 순서로 마감한다.

실명 담당자와 최종 발표 형식은 팀 확인이 필요하지만, 위 자료 정리·단순 모듈 연결·입출력 구성·개인정보 없는 평가 준비는 그 결정을 기다릴 필요가 없다. 사진 원본 외부 전송은 비식별 작업본과 전송 권한 확인을 마친 뒤 진행한다.


## 10. 팀 합의 방향 — 가진 자료에서 마무리하기

- **비교 기준:** “1차 후보 기반 6곳안”과 “2차 생활권 분석 9곳안”으로 구분한다. 1차 조사에서 발굴한 후보 전체는 11곳이고, 그중 선택한 6곳이 비교안이다. 1차 후보 자체가 6곳뿐이었다고 표기하지 않는다.
- **대표 추천:** 2차 분석의 9곳안을 사용한다. 기존 후보6곳과 새 대안3곳으로 구성하며, 주민 접근성을 우선한 현재 자료 범위의 추천이다. 비용·부지·현장 운행까지 검증한 절대 최적이라는 뜻은 아니다.
- **결과 연결 단계:** 팀의 실제 분석 산출물(GeoJSON·엑셀·요약)을 검색·지도·배정 안내에 연결하는 작업이다. 현장 시설 설치나 수거차 실운행을 요구하는 단계가 아니다. 현재 프로젝트는 이 연결을 이미 수행했다. 남은 것은 최종 화면과 원본 수치 대조다.
- **이번 검증:** 팀 내부에서 기능·계산값·출처·오류/보류·다른 PC 실행을 확인한다. 주민 실증·현장 안전 인증·지자체 운영 검증으로 표현하지 않는다.
- **제출 방향:** 확보 자료와 구현 결과를 기준으로 소프트웨어 시연을 마무리하고, 실제 도입은 별도 액션플랜으로 제시한다. 현장 결과를 새로 확보해야만 제출 완료가 되는 구조로 만들지 않는다.

### 도입을 위한 후속 액션플랜 — 이번에 실행 완료했다고 주장하지 않을 항목

1. 9곳안의 위치·수요·접근거리·미확인 조건을 후보 검토표로 정리해 전달한다.
2. 지자체·부지 관리 주체·수거 담당자와 검토할 항목을 합의한다: 사용 가능 공간, 작업면, 차량 조건, 보행 영향, 관리 책임·비용.
3. 합의된 조건으로 적용 가능한 구간과 시험 운영 범위를 정한다. 배치안 변경이 필요하면 기존 지표로 다시 비교한다.
4. 시험 운영을 한다면 배출량·주민 이동/불편·수거 작업시간·관리비·민원을 기록할 기준을 먼저 정한다.
5. 그 기록을 바탕으로 유지·조정·확대 여부를 결정한다.

위 다섯 항목은 앞으로 누가 어떤 근거로 의사결정할지 설명하는 계획이다. 이번 팀 프로젝트의 미완료 개발 목록에 넣지 않는다.
